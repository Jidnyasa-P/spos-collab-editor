Race Lab

Run the same job twice, side by side: once with nothing protecting the shared data, and once with the reader-priority lock from the editor. Everything is slowed down so you can watch it happen.

  1. Press Run both. Several writers each add 1 to a shared counter, and readers keep checking that the counter and its mirror copy agree.
  2. Watch the left side. Amber chips are writing. When two writers collide, the log reports a lost update.
  3. Compare the final numbers. The correct counter is writers times increments.

What you are looking at

A lost update

Two writers read the same value, both add one, and both write the same answer. One increment is gone, and nothing reports an error. This is the classic race condition.

counter = 5
Writer A reads 5      Writer B reads 5
Writer A writes 6     Writer B writes 6   (should be 7)

An inconsistent read

A reader looks at the counter and its mirror while a writer has changed only one of them. The reader sees a state that was never meant to exist. In a document this would be half of an edit.

How the lock fixes both

A writer takes the write lock before it reads and releases it only after both values are updated. Writers take turns, and no reader can slip in the middle. Readers share the read side, so they never block one another.

The price: reader priority

While any reader is inside, new readers walk straight in and a waiting writer has to wait. Tick Busy readers and run again to watch writers wait for seconds. That is starvation, the known weakness of this variant.
